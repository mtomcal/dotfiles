# Audit activity and reference-centric skills

## Question
What is the smallest reliable shape for command manuals and runner recipes that may legitimately omit Workflow?

## Why it matters
Forcing tool catalogs into an end-to-end process would obscure selectable commands, while leaving all details inline may waste context and duplicate recipes.

## Completion evidence
Comparable audit records and one evidenced recommendation exist for `herdr`, `playwright`, and `ralph`. The recommendations distinguish essential discovery and safety rules from reusable Activities and load-on-demand Reference material, while preserving provenance and executable command accuracy.

## Resolution
### herdr
- Profile / disclosure: Activity catalog; overloaded.
- Authorities: Frontmatter triggers only inside a Herdr-managed pane (`HERDR_ENV=1`); `specs/ai-agent-config.md` requires delegating skills to load the shared Herdr skill and forbids persisting compact pane identifiers; `specs/herdr-config.md` requires cross-agent distribution; Herdr terms are defined in `specs/UBIQUITOUS_LANGUAGE.md`. The body matches upstream `ogulcancelik/herdr` commit `6cbdba434fd1` except for repository frontmatter, introduced locally by commit `1007795`; upstream is AGPL-3.0-or-later, but `THIRD_PARTY_NOTICES.md` contains no Herdr provenance or license entry. Supporting authority is the linked socket API and the installed Herdr 0.7.1 CLI.
- Baseline: 303 lines; 1,449 words; 12 level-two headings outside fences (`concepts`, discovery, tab management, pane reading/splitting, two wait forms, input, workspace management, pane closing, recipes, notes); 1 external Markdown-style link and no local Markdown references.
- Behavior ledger:
  - Language: Defines workspaces, tabs, panes, `agent_status`, `done`, and compact workspace/tab/pane IDs. Workspace/tab/pane duplicate repository-domain definitions. Material **Language Definition candidates** are **caller pane/current pane**, **public Herdr ID**, **legacy display ID**, and the `idle`/`done` distinction. Current live state disproves “the focused pane is yours”: `HERDR_PANE_ID` identified the caller while `herdr pane list` marked a different UI-focused pane. Current upstream now treats `w…` identifiers as opaque public IDs and numeric forms as legacy selectors, conflicting with the skill’s compaction model and the rationale in `specs/ai-agent-config.md`.
  - Workflow/routing: No required end-to-end workflow. The entry gate stops outside `HERDR_ENV=1`; otherwise users independently select discovery, workspace/tab management, pane inspection, splitting/running, waiting, input, closing, or coordination recipes. Recipes complete by waiting for expected output/status and reading the resulting transcript.
  - Activities: Discover workspaces/tabs/panes; create, label, focus, rename, and close workspaces/tabs; read visible, rendered recent, or unwrapped recent pane output; split right/down without moving focus; parse the created pane ID and run commands; wait for literal/regex output; wait for agent state; send text, keys, or text-plus-Enter; close panes; run servers/tests; inspect or spawn agents; coordinate with another agent. Current Herdr 0.7.1 help confirms all named command families and listed options. Live smoke checks confirmed all three read sources and JSON list response shapes.
  - Inline contracts: Must verify `HERDR_ENV=1`; IDs must be refreshed after mutations; `--no-focus` preserves the caller’s context; parse IDs from JSON; `pane read` emits text, list/create/get/split/wait commands emit JSON, and send/run commands are silent; inspect existing output before waiting; timeout exits `1`; rendered versus unwrapped output must match the task. The skill lacks explicit approval/ownership guards before destructive close/focus operations.
  - Reference: The socket API is conditional on needing raw protocol or full API details. No local progressive-disclosure reference exists.
- YAGNI findings: The split/run sequence is repeated in the main command section and server recipe; pane read/wait rules recur in command sections, recipes, and notes; test and agent recipes repeat the same split → run → wait → read operation. Static numeric examples remain accepted as legacy selectors but can resolve by display position and therefore undermine the skill’s own “do not guess IDs” guardrail. Two recipes split and then assume `1-3` rather than parsing the returned ID. Static command detail has also drifted from current official guidance, which now uses `HERDR_PANE_ID`, `--current`, opaque `w…` IDs, dynamic CLI discovery, and stronger ownership rules. Imported AGPL material has no required repository provenance.
- Recommendation: **simplify inline**. Proposed shape:
  - `## Language Definitions`: Define only caller/current pane, opaque public ID versus legacy display selector, and agent completion status; refer to `specs/UBIQUITOUS_LANGUAGE.md` rather than redefining workspace/tab/pane.
  - `## Workflow`: Omit.
  - `## Activities`: Start with the environment gate and current-context discovery; then provide compact activities for inspect/read, split/run/send, wait/diagnose, and explicitly requested workspace/tab/resource management. Make installed CLI help authoritative, use `HERDR_*_ID` or `--current`, parse every mutation response, preserve `--no-focus`, and require approval before closing resources not created by the agent. Collapse server, test, and agent examples into the shared split → parse → run → wait → read recipe with task-specific substitutions.
  - `## Reference`: Point conditionally to upstream `SKILL.md` when validating command/version behavior and provenance; keep raw socket documentation out of the main path and load it only for protocol work.
  Also record the upstream revision and AGPL attribution in `THIRD_PARTY_NOTICES.md`; do not blindly adopt upstream’s narrower explicit-user trigger because repository workflows intentionally compose this skill for delegation.
- Preservation and risk: Discovery, all workspace/tab/pane operations, all read formats, command and agent launching, both wait modes, input forms, output contracts, timeout behavior, focus preservation, and coordination remain in the Activities or beside their governing operation. Duplicate recipes become parameterized examples rather than disappearing. The main risks are changing the repository-wide meaning of Herdr IDs and `done`; those Language Definition candidates require human confirmation and corresponding spec review. Confidence: high, based on installed CLI help, live read-only responses, upstream source/history, and repository specs.

### playwright
- Profile / disclosure: Activity catalog; overloaded.
- Authorities: Frontmatter triggers explicit Playwright requests, deterministic browser automation, recordings, and existing Playwright test setups; it routes visual judgment to `visual-qa` and recording review to `video-to-contact-sheet`. `specs/tool-provisioning.md` and `specs/install-orchestrator.md` install `@playwright/cli@latest`; `specs/ai-agent-config.md` governs cross-agent frontmatter and imported provenance. The skill was introduced in commit `236096b`, substantially adapted from Microsoft’s bundled `microsoft/playwright-cli` skill around commit `fac6ebbe6816`, then renamed/rerouted in commit `26119db`. Microsoft’s package is Apache-2.0, but `THIRD_PARTY_NOTICES.md` contains no Playwright attribution. Supporting files are all nine Markdown files under `shared/skills/playwright/references/`.
- Baseline: 369 lines; 1,143 words; 13 level-two headings outside fences (`Quick start`, binary fallback, commands, raw output, open parameters, snapshots, targeting, sessions, installation, three examples, specific tasks); 9 Markdown references. The linked corpus adds 1,194 lines and 3,846 words, for 1,563 lines and 4,989 words overall.
- Behavior ledger:
  - Language: Uses browser session, persistent profile, snapshot, ref/target, storage state, route, trace, raw output, and recording without a consolidated definition. Material **Language Definition candidates** are **browser session**, **snapshot**, **element ref**, **persistent profile**, and **storage state** because they control state lifetime and command targeting.
  - Workflow/routing: No single mandatory workflow. Initial routing redirects pass/fail visual review and recording post-processing to owning skills. A quick browser activity opens, navigates, targets from a snapshot, interacts, optionally captures, and closes. Conditional branches cover missing native browser libraries, local-versus-global CLI discovery, debugging existing tests, raw scripts, named sessions, and specialized capture or mocking tasks.
  - Activities: Core navigation and interaction; keyboard/mouse input; screenshots/PDFs; tabs; cookies and web storage; routing/mocking; console/network inspection; arbitrary Playwright code; traces and videos; raw/JSON-like shell output; browser selection/configuration/attachment; snapshots and element targeting; named/persistent sessions and cleanup; installation; form, multi-tab, and debugging examples; Playwright test execution/debugging.
  - Inline contracts: Prefer snapshot refs; snapshots are the normal inspection surface; use a system browser before privileged dependency installation; keep debug tests running in the background and stop them afterward; clean up browser sessions; use `--raw` when piping; storage-state files can contain credentials and must not be committed; generated tests need manual assertions; traces and recordings add overhead and need cleanup. Outputs include snapshots, screenshots, PDFs, storage JSON, trace files, WebM recordings, generated TypeScript, raw values, and test results. Privileged dependency installation is cautioned but not explicitly approval-gated.
  - Reference: Nine conditional topics exist: test running/debugging, request mocking, custom code, session management, storage, test generation, tracing, recording, and element attributes. Their list names topics but does not consistently state load conditions.
- YAGNI findings: The main file duplicates almost every reference family: storage commands repeat `references/storage-state.md`; sessions repeat `references/session-management.md`; routing repeats `references/request-mocking.md`; custom code, tracing, video, test generation, and attribute inspection similarly recur. Quick start, command tables, and three examples repeat one another. Static command documentation drifts because installation tracks `@latest`: installed 0.1.14 and current npm 0.1.17 expose `requests`/`request`, while the skill’s `playwright-cli network` merely returns top-level help; `references/video-recording.md` uses invalid `run-code --file` instead of confirmed `--filename`. Current upstream has already corrected both. The binary fallback uses `which`, while frontmatter only permits `playwright-cli`, `npx`, and `npm` Bash patterns. Imported Apache-2.0 documentation lacks repository-level provenance and attribution.
- Recommendation: **move detail to Reference**. Proposed shape:
  - `## Language Definitions`: Define browser session, snapshot, element ref/target, persistent profile, and storage state.
  - `## Workflow`: Omit.
  - `## Activities`: Keep initial routing; a minimal open → snapshot → interact → verify/capture → close activity; CLI availability and browser-launch recovery; existing-test execution/debugging; and cleanup/security guardrails. Use `playwright-cli --help <command>` as the command-syntax authority rather than maintaining an exhaustive inline manual.
  - `## Reference`: Retain the nine topic references with explicit “load when” conditions; consolidate the exhaustive command index, raw output, open/session parameters, and specialized examples into reference material. Correct or retire stale commands before treating references as executable.
  Record Microsoft provenance and Apache-2.0 attribution in `THIRD_PARTY_NOTICES.md`.
- Preservation and risk: Main-path browser automation remains independently executable. Every specialized behavior moves to its existing topic reference: tests/debugging, mocking, custom code, sessions, storage/security, generated tests/assertions, tracing, video, and attribute inspection. Installation and browser fallback remain beside their failure gate. Routing to visual-review owners stays at the beginning. The primary risk is version skew under `@latest`; dynamic help plus tested reference updates are required. Language candidates need human confirmation. Confidence: high on structure, duplication, provenance, and identified command failures; medium on commands requiring a live browser because no stateful browser session was launched during this read-only audit.

### ralph
- Profile / disclosure: Artifact workflow; progressively disclosed.
- Authorities: Frontmatter triggers configuring or launching a loop job built from `PROMPT.md`, `IMPLEMENTATION_PLAN.md`, and `ORCHESTRATOR.md`. `specs/parameters.md` defines `RALPH_DEFAULT_ITERATIONS=25` and `RALPH_DONE_PATTERN=/done`; the plan-workspace contract in `specs/ai-agent-config.md` applies if `IMPLEMENTATION_PLAN.md` is intended as an active implementation plan. Git provenance is local commit `dfd67d2`, later moved into shared skills by `4fcd8db`; no repository evidence identifies imported text or a required third-party license. Supporting code is `shared/skills/ralph/references/loop.sh`; the shared test-quality workflow is referenced by name.
- Baseline: 30 lines; 199 words; 3 level-two headings outside fences (`Files`, `Launch`, `PROMPT.md Rules of Thumb`); 0 Markdown references. The shell template adds 58 lines and 191 words and is tracked as non-executable mode `100644`.
- Behavior ledger:
  - Language: Introduces loop job, iteration, worker, orchestrator, plan, course correction, and `/done`. Material **Language Definition candidates** are **Ralph job**, **worker iteration**, **Ralph job plan**, **orchestrator**, and **done sentinel**. “Plan” must be qualified so `IMPLEMENTATION_PLAN.md` is not confused with the repository’s defined plan workspace.
  - Workflow/routing: Intended order is configure three job artifacts, copy/use the generic runner, launch with an iteration bound and prompt path, then repeatedly run one fresh Codex execution that reads the prompt, performs one checklist item, updates the plan, commits, and exits. An optional orchestrator monitors logs/Git and prepends course corrections. Completion occurs when worker output contains `/done`.
  - Activities: No independently selectable Activities are established. Launch is a Workflow step; course correction is described but not executable as a separate recipe.
  - Inline contracts: Keep the prompt concise; reference the plan first; put `IMPORTANT:` corrections first; process one checklist item per iteration; update the plan with progress/discoveries; run the test-quality workflow after test changes; emit `/done` exactly on completion. The runner creates `.loop-logs`, validates Codex and prompt-file presence, invokes `codex exec --full-auto --sandbox`, records each iteration through `tee`, captures Codex’s pipeline status, and supports three sandbox modes. Non-zero Codex exits are logged but the loop continues. No validation exists for iteration syntax or dangerous sandbox selection.
  - Reference: No Markdown reference. The shell template is a required supporting artifact and should remain linked beside the setup/launch step rather than being misclassified as Reference.
- YAGNI findings: The skill is compact, but several claims lack executable support. `ORCHESTRATOR.md` is required by the advertised file set while no template or monitoring process is supplied. The stated launch command assumes an executable local `loop.sh`, while the supplied template is non-executable and no copy/chmod step exists. The template defaults to unlimited iterations, contradicting `RALPH_DEFAULT_ITERATIONS=25`. `grep -q "/done"` accepts substrings rather than the promised exact sentinel. A Codex failure says to fix the problem but automatically proceeds to the next iteration. The intro promises one commit per iteration, but the prompt rules do not require or verify a commit. `danger-full-access` is selectable without approval. The job-plan/orchestration model also overlaps `create-plan`; per WF-002, catalog-wide ownership should be deferred to WF-006, with `create-plan` recorded as the candidate owner.
- Recommendation: **simplify inline**. Proposed shape:
  - `## Language Definitions`: Define Ralph job, worker iteration, Ralph job plan, orchestrator, and exact done sentinel; distinguish the job plan from the repository plan workspace.
  - `## Workflow`: One ordered process covering applicability, artifact setup, runner copying/permission validation, prompt contract, bounded launch, iteration monitoring, course correction, failure handling, exact completion detection, and final Git/test evidence. Default to the specified 25 iterations, stop on invalid arguments or non-zero Codex exit, require approval for `danger-full-access`, and align the commit claim with enforceable prompt/evidence requirements.
  - `## Activities`: Omit unless course correction is later made independently invocable.
  - `## Reference`: Omit; keep `references/loop.sh` beside the setup/launch step because it is executable support, not Markdown reference material.
  Remove `ORCHESTRATOR.md` from the required default artifact set unless a concrete monitoring contract/template is retained. Record the overlap with the plan-control workflow for WF-006 rather than consolidating now.
- Preservation and risk: The three-artifact concept, one-item iterations, repeated prompt reads, progress/discovery updates, logs, sandbox selection, test-quality routing, course corrections, commit intent, and `/done` completion all remain in the Workflow or runner contract. Corrections address contradictions rather than deleting intended behavior. Dependencies are current Codex CLI, Git, the test-quality skill, and the parameters/spec contracts. The principal risk is silently treating a Ralph job plan as a spec-governed plan workspace; terminology and ownership need human confirmation. Confidence: high, based on shell syntax validation, current Codex help, file mode, Git provenance, and parameter/spec comparison.

Coverage: **3/3 assigned skills; 9/9 directly linked Markdown files; 1/1 supporting shell template; 3/3 provenance trails; 3/3 command surfaces checked where possible. No files or Wayfinder state changed.**
