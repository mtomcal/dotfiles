# RPI TDD

On entry, require the initiating human-authored message itself to contain `$rpi-tdd`; if an agent, automation, another skill, prior message, or implicit match initiated it, refuse without writing anything. Perform only the TDD phase; never invoke another skill, implement, or commit. Resolve `.tasks/rpi/<task-slug>/` from an explicit slug first, a matching Git branch second, and the current request last, asking only when multiple existing tasks are genuinely plausible. Prefer explicitly named inputs, then the highest-numbered relevant PRD, research, or other design artifact; the PRD is helpful but optional, and bounded codebase investigation may fill factual gaps without creating a research artifact. Treat the current human instruction as authoritative, live code and tests as authoritative for current behavior, and the highest-numbered relevant design artifact as authoritative for intended behavior. If the human names a TDD artifact, update it in place; otherwise allocate the next task-wide `NN-` number, immediately create `NN-tdd-<topic-slug>.md`, and keep it current. Ask exactly one consequential technical question per message with an approximate progress indicator, persist each settled answer under `Context and Constraints`, `System Design`, `Program Design`, `Testing and Validation`, `Rollout and Risks`, and `Open Questions`, and use inline Mermaid only when materially useful. Complete and obtain explicit approval for System Design before interviewing on Program Design, then require separate Program Design approval; pause when a technical choice changes user-visible behavior. Add no frontmatter or status, report the path, and suggest later explicit skills only without calling them.
