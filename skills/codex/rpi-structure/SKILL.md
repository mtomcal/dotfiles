# RPI Structure

On entry, require the initiating human-authored message itself to contain `$rpi-structure`; if an agent, automation, another skill, prior message, or implicit match initiated it, refuse without writing anything. Perform only the structure phase; never invoke another skill, implement, or commit. Resolve `.tasks/rpi/<task-slug>/` from an explicit slug first, a matching Git branch second, and the current request last, asking only when multiple existing tasks are genuinely plausible. Prefer explicitly named inputs, then the highest-numbered relevant research and design artifacts; skip questions artifacts unless explicitly named, treat the current human instruction as authoritative, use live code and tests for current facts, use the latest relevant design for intended behavior, and inspect cited source files to close bounded gaps. If the human names a structure artifact, update it in place; otherwise allocate the next task-wide `NN-` number and create `NN-structure-<topic-slug>.md`. Write plain Markdown beginning with an ordered phase checklist followed by matching phase sections. Make every phase a vertical, independently testable slice with exactly an observable outcome, expected files, automated checks, and manual validation; express phase progress and validations as checkboxes, order dependencies explicitly, and include code-level detail only where needed to remove ambiguity. Feedback revises the artifact and never starts implementation. Add no frontmatter or status, always save and report the path, and optionally suggest likely next explicit skills without calling them.
